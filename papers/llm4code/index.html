Are Large Language Models Memorizing Bug Benchmarks?

Daniel Ramos, Claudia Mamede*, Kush Jain*, Paulo Canelas*, Catarina Gamboa*, Claire Le Goues

LLM4Code 2025 - International Workshop on Large Language Models for Code. *Equal contribution.

Paper (arXiv) PDF Cite Best Paper Award

Bug benchmarks like Defects4J have been public for years, so models may have seen the answers. We tested 9 open models on 5 bug benchmarks and on new code from 2024. Defects4J shows the strongest signs of memorization.

    Three signals of leakage

    Training data is rarely public, so no single test can prove a model saw a benchmark. We combine three signals. Pick one.

    Is the benchmark's repository in TheStack, a pretraining dataset that models like StarCoder 2 report using?

    Table view (Table III)

    Negative log-likelihood measures how surprised a model is by each next token. Code it has seen many times scores close to zero.

    int main Next token?

    Pick a next token (the example from Figure 2).

    NLL depends on the tokenizer, so we only compare it within a model family.

    5-gram accuracy: give the model the file up to a point and check whether its next 5 tokens match the real ones. 1.0 means it reproduces the file verbatim.

    Ground truthdef __init__(self, *, qop: str = None,
    LLaMa 3.1 70Bdef __init__(\nself, \n*, \nqop: str = None \n,

    No match on __init__(self,, even though the code is the same. Only the line breaks differ (BugsInPy, fastapi bug 12).

    That is why a low 5-gram score alone does not rule out memorization, and why we use all three signals.

    What we recommend

    • Pair Defects4J with recent benchmarks such as GitBug-Java.
    • Re-check membership, NLL and 5-gram accuracy as pretraining data grows.
    • Read the signals together: no single one gives the full picture.
